# Deployment Guide

This document covers three deployment targets for the Drilling Costing application:

1. **Cloud** — Vercel (Nuxt SSR) + Render (FastAPI) + Neon (PostgreSQL 16)
2. **Local PC** — Direct Python + Node.js + PostgreSQL
3. **Termux (Android)** — Run the app on a phone over Wi-Fi/LAN

---

## 1. Cloud Deployment (Vercel + Render + Neon)

See [docs/deployment/free-uat-vercel-render-neon.md](docs/deployment/free-uat-vercel-render-neon.md)
for the full free UAT walkthrough.

### Quick reference

| Layer | Provider | Configuration file |
|---|---|---|
| Frontend SSR | Vercel Hobby | `frontend/vercel.json` |
| API server | Render Free | `render.yaml` |
| Database | Neon Free | — |

### Environment variables required

**Render (backend):**
- `ENVIRONMENT=uat`
- `DATABASE_URL` — Neon pooled URL
- `MIGRATION_DATABASE_URL` — Neon direct URL
- `SECRET_KEY` — Auto-generated by Render
- `CORS_ORIGINS` — JSON array of allowed frontend origins
- `BOOTSTRAP_ADMIN_EMAIL` — Initial admin email (remove after first use)
- `BOOTSTRAP_ADMIN_PASSWORD` — Initial admin password (remove after first use)

**Vercel (frontend):**
- `NUXT_PUBLIC_API_BASE=/api/v1`
- `NUXT_API_INTERNAL_BASE` — Render service URL
- `NUXT_API_PROXY_TIMEOUT_MS=90000`

## 2. Local PC Deployment (Linux / macOS)

### Prerequisites

- Python 3.12+
- Node.js 22 LTS+
- PostgreSQL 16 (with `psql`)
- Git

### Setup

```bash
# 1. Clone the repository
git clone <repository-url> drilling-costing
cd drilling-costing

# 2. Backend setup
cd backend
python -m venv .venv
source .venv/bin/activate  # Windows: .venv\Scripts\Activate.ps1
pip install -e ".[dev]"

# 3. Create PostgreSQL database
psql -U postgres
CREATE ROLE drilling_costing WITH LOGIN PASSWORD 'your-password';
CREATE DATABASE drilling_costing OWNER drilling_costing;
\q

# 4. Configure backend/.env
cp .env.example .env
# Edit .env: set DATABASE_URL, SECRET_KEY
```

```bash
# 5. Run migrations
alembic upgrade head

# 6. Seed a local user
export SEED_USER_EMAIL="admin@example.com"
export SEED_USER_PASSWORD="your-password"
export SEED_USER_FULL_NAME="Local Administrator"
python scripts/seed_user.py

# 7. Start backend
uvicorn app.main:app --reload --host 0.0.0.0 --port 8000
```

```bash
# 8. Frontend setup (new terminal)
cd frontend
npm install
npm run dev -- --host 0.0.0.0
```

Open http://localhost:3000 and sign in.

### One-command start script (Linux/macOS)

```bash
#!/usr/bin/env bash
# start-dev.sh — Start both servers for local development
set -euo pipefail

REPO_DIR="$(cd "$(dirname "$0")" && pwd)"

echo "Starting backend..."
cd "$REPO_DIR/backend"
source .venv/bin/activate
uvicorn app.main:app --reload --host 0.0.0.0 --port 8000 &
BACKEND_PID=$!

echo "Starting frontend..."
cd "$REPO_DIR/frontend"
npm run dev -- --host 0.0.0.0 &
FRONTEND_PID=$!

echo "Backend:  http://localhost:8000"
echo "Frontend: http://localhost:3000"
echo "API docs: http://localhost:8000/docs"
echo ""
echo "Press Ctrl+C to stop both servers."

trap "kill $BACKEND_PID $FRONTEND_PID 2>/dev/null; exit" INT TERM
wait
```

Save as `start-dev.sh` and make executable:
```bash
chmod +x start-dev.sh
./start-dev.sh
```

## 3. Termux (Android Phone) Deployment

### What is Termux?

Termux is an Android terminal emulator and Linux environment app. It lets you run
Python, Node.js, and PostgreSQL on your phone — turning it into a development/test
server for the LAN.

### Prerequisites

- Android 8+ device (preferably with 4+ GB RAM, ~3 GB free storage)
- [Termux](https://f-droid.org/repo/com.termux_118.apk) from F-Droid (NOT Google Play — it's outdated)
- [Termux:API](https://f-droid.org/repo/com.termux.api_51.apk) (recommended for Wi-Fi detection)
- Wi-Fi connection (LAN access) or cellular data (localhost only)

> **Why Debian inside Termux?** PyPI has no wheels for Termux's bionic Python, so
> installing the backend natively compiles `pydantic-core` (Rust) and friends from
> source — that's the "stuck in step 2" hang. The scripts therefore run the Python
> backend inside a `proot-distro` Debian container (installed automatically), where
> every package in `backend/pyproject.toml` installs as a prebuilt
> `manylinux_aarch64` wheel. The frontend stays on Termux-native Node.js. See
> [termux/README.md](termux/README.md) for the full explanation.

### Quick start

```bash
# 1. Install Termux from F-Droid, open it, then run:
pkg update -y
pkg install -y git

# 2. Clone the repository
git clone <repository-url> drilling-costing
cd drilling-costing

# 3. Run the Termux setup script
#    (installs proot-distro Debian + the backend Python environment inside it)
bash termux/setup.sh

# 4. Edit backend/.env with your Supabase database URL
#    (or skip for SQLite development — see below)
nano backend/.env

# 5. Run database migrations
bash termux/migrate.sh

# 6. Seed a local user (the backend venv lives inside the Debian container;
#    backend-exec.sh runs any backend command there and forwards SEED_USER_*)
SEED_USER_EMAIL="admin@example.com" \
SEED_USER_PASSWORD="your-password" \
SEED_USER_FULL_NAME="Termux Admin" \
  bash termux/backend-exec.sh python scripts/seed_user.py

# 7. Start the servers
bash termux/start.sh
```

Open http://localhost:3000 on the phone, or `http://<phone-ip>:3000` from any device
on the same network.

### Termux troubleshooting

#### Problem: Python setup hangs on `pydantic-core` / `watchfiles` (Rust builds)

Termux's Python uses Android's bionic libc, for which PyPI publishes **no wheels**.
pip then tries to compile `pydantic-core`, `watchfiles`, `uvloop`, etc. from Rust/C
source on the phone — this runs for 15+ minutes and usually fails
(out-of-memory or linker errors). This cannot be fixed with pip flags.

**Solution (built into the scripts):** the backend runs inside a `proot-distro`
Debian container — a real glibc Linux where every dependency installs as a
prebuilt `manylinux_aarch64` wheel. The scripts install and manage the container
automatically; no native compilation ever happens.

If you have a broken legacy environment, clean it and redeploy:

```bash
bash termux/stop.sh || true
rm -rf backend/.venv backend/.venv-debian termux/.setup_done
bash termux/deploy.sh
```

#### Problem: `proot-distro` install fails or Debian won't start

```bash
# Update Termux itself first, then retry
pkg update -y && pkg upgrade -y
pkg install -y proot-distro
proot-distro install debian

# If the container is corrupted, reset it and redeploy:
proot-distro reset debian
rm -f termux/.setup_done
bash termux/deploy.sh
```

The project uses the pure-Python `psycopg` driver (not `psycopg[binary]`), so no
libpq build toolchain is needed inside the container either.

#### Problem: Port 3000 or 8000 already in use

Find and kill the process:

```bash
pkill -f "uvicorn" || true
pkill -f "nuxt" || true
pkill -f "node" || true
pkill -f ".output/server" || true
```

Or use the stop script:
```bash
bash termux/stop.sh
```

#### Problem: Can't access from other devices on the LAN

1. Ensure the phone and target device are on the **same Wi-Fi network**.
2. Find the phone's LAN IP:
   ```bash
   ip addr show wlan0
   # Look for "inet 192.168.x.x"
   ```
3. Verify `CORS_ORIGINS` includes `http://<phone-ip>:3000` in `backend/.env`.
4. Some routers have "client isolation" — check router settings if the device can't connect.

#### Problem: Backend won't start — port already taken

```bash
# Check what's using port 8000
lsof -i :8000 || ss -tlnp | grep 8000

# Kill it
fuser -k 8000/tcp
```

#### Problem: Database connection refused

The Termux setup uses Supabase (cloud PostgreSQL) by default. If you don't have
or want Supabase, comment out `DATABASE_URL` in `backend/.env` and the app will
attempt to connect to the default value — but a local PostgreSQL is needed.

**Option A: Use Supabase (recommended for Termux)**
1. Create a free Supabase account.
2. Go to Project Settings → Database → Connection string.
3. Copy the "Transaction pooler" URI (port 6543).
4. Update `DATABASE_URL` in `backend/.env`.

**Option B: Local PostgreSQL on Termux**
```bash
pkg install -y postgresql
initdb ~/postgres-data
pg_ctl -D ~/postgres-data -l ~/postgres-log start
createdb drilling_costing
# Update backend/.env:
# DATABASE_URL=postgresql+psycopg:///drilling_costing
```

#### Problem: Memory/RAM errors

Termux on devices with less than 4 GB RAM can struggle with `npm run build`.
Workarounds:

```bash
# Use development mode (no build needed)
export TERMUX_DEV=1
bash termux/start.sh

# Or limit Node.js memory
export NODE_OPTIONS="--max-old-space-size=1024"
```

#### Problem: Nuxt build fails with out-of-memory

```bash
# Clear npm cache and retry with limited memory
npm cache clean --force
export NODE_OPTIONS="--max-old-space-size=1024"
rm -rf .output
npm run build
```

#### Problem: Keyboard not showing in Termux

Swipe from the left edge of the Termux window to open the keyboard.
If it doesn't appear, long-press the screen and select "Keyboard".

#### Problem: Battery drain

The servers keep the CPU awake. When not in use:

```bash
bash termux/stop.sh
```

### Using SQLite for local-only Termux development

If you don't want to set up PostgreSQL/Supabase, you can modify the
`DATABASE_URL` in `backend/.env` to use SQLite:

```
DATABASE_URL=sqlite:///./dev.db
```

**Note:** This changes the database dialect. Some Alembic migrations use
PostgreSQL-specific features. Running `alembic upgrade head` with SQLite
may fail. For full functionality, use PostgreSQL.

## 4. Database Configuration

### Environment variables

| Variable | Purpose | Required |
|---|---|---|
| `ENVIRONMENT` | Runtime environment (`development`, `test`, `termux`, `uat`, `staging`, `production`) | Yes |
| `DATABASE_URL` | Runtime database URL | Yes |
| `MIGRATION_DATABASE_URL` | Direct database URL for Alembic (use with poolers) | Optional |
| `SECRET_KEY` | JWT signing secret (min 32 chars) | Yes |

### Database URL formats

```text
# Local PostgreSQL
postgresql+psycopg://user:password@localhost:5432/drilling_costing

# Neon pooled (recommended for cloud)
postgresql+psycopg://user:password@aws-0-region.pooler.supabase.com:6543/postgres

# Neon direct (for migrations)
postgresql+psycopg://user:password@aws-0-region.supabase.com:5432/postgres

# Supabase pooled
postgresql+psycopg://postgres.xxxx:password@aws-0-region.pooler.supabase.com:6543/postgres

# SQLite (development only, limited compatibility)
sqlite:///./dev.db
```

### Supabase Auth sign-in (optional)

When the backend database is a Supabase project, users created in **Supabase
Authentication** can sign in through the normal login page with their Supabase
email and password. Add to `backend/.env`:

```text
SUPABASE_URL=https://<project-ref>.supabase.co
SUPABASE_ANON_KEY=<project settings → API → anon public key>
```

Login still checks the application's own `users` table first, so provisioned
users and the bootstrap administrator keep working. When the local check does not
match — or the user has no local password hash because it was created in Supabase —
the backend validates the credentials against Supabase Auth and mirrors the
identity into `users` with `auth_provider='supabase'`. The password itself is
never stored in the application database.

## 5. CI/CD

The repository includes a GitHub Actions workflow (`.github/workflows/ci.yml`)
that runs on every push. It executes:

- Ruff linting (Python)
- Pyright type checking
- Pytest with coverage
- ESLint (frontend)
- Nuxt type checking
- Vitest (frontend unit tests)

Render deploys automatically when CI passes on `main`.

## 6. Health check endpoints

After deployment, verify these endpoints:

| Endpoint | Purpose |
|---|---|
| `GET /api/v1/live` | Application is running |
| `GET /api/v1/ready` | Application + database are ready (HTTP 503 if DB down) |
| `GET /api/v1/health` | Compatibility endpoint (degraded = DB unavailable) |
